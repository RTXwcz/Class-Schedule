# v1.6.4 导入落地验证

用户反馈：识别出十几门课，应用到课表后“只导入了一门”。本次复现并修好了这个落地问题。日期为 2026-09-11。

## 复现

用真实截图跑完整链路（解析 → 真实数据库导入）：

```
IMPORT-DEBUG parsed=14
IMPORT-DEBUG applied=0 error=第 5 门课程：结束节次超出当前作息（共 12 节），请修改节次或调整作息
```

结论：**导入以前是全有或全无**。这批课程里 `创业基础` 是第 11–13 节，而应用当前作息只有 12 节，校验失败导致整批回滚，看起来就像“只导入了一门/什么都没进去”。

## 修复

1. **可用先落库**：把草稿分成「可应用」和「待补充」，可应用的课程照常写入数据库，待补充的留在复核列表并说明原因；状态栏显示「已追加 N 门课程，M 门待补充」。
2. **提示可执行的下一步**：如果原因是节次超出当前作息、而图片又识别到了作息（时间轴），错误提示会补上“可先点上方‘应用为每日作息’（识别到 13 节）再应用识别结果”。
3. **节次不再留空**：结构判断不出跨度时，过去把结束节次留空，导致整批无法应用；现在按“至少占用起始那一节”填入并把置信度降到 0.55，复核页仍把它标为需要确认。

修复后同一批数据：

```
IMPORT-DEBUG step1 applied=13 kept=1 status=已追加 13 门课程，1 门待补充
IMPORT-DEBUG step2 applied=14 kept=null status=已追加 1 门课程
```

step2 是把识别到的 13 节作息应用为每日作息后再导入剩余课程。

## 验证证据

| 检查 | 结果 |
| --- | --- |
| 真实截图端到端 | 先落库 13 门、保留 1 门待补充；补齐作息后 14 门全部入库 |
| 单元测试 | 103 项全部通过（含“无效课程保留在复核列表且给出原因”） |
| Android 15 设备测试 | 67 项全部通过 |
| 新增真机回归 | `ImportApplyPersistenceTest`：用 Room 内存库验证可导入课程落库、超作息课程留在复核、补齐作息后剩余课程成功入库 |

## 已知边界

- 「待补充」的课程需要在复核页补齐字段后再次点“应用识别结果”。
- 云端识别与本地识别的落地逻辑一致，同样遵循“可用的先入库、其余留待确认”。
